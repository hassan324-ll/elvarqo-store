## Accounts and ownership
Separate customer identities, hashed session capabilities, authentication version, email verification/recovery/change challenges, address book, wishlist and explicit order ownership links. Next allowlisted same-origin JSON proxies store only host-only HttpOnly customer cookies, isolated from staff/bag/tracking cookies. Session idle two hours, absolute fourteen days; logout/password reset revoke sessions. Password hashing and bounded neutral recovery/registration responses; verification/reset/claim tokens are single-use thirty-minute hashed records delivered through encrypted durable private email copies. Staff guard or typed matching email cannot authorize a customer order. Explicit order-claim proof is sent to the immutable order email, bound to the signed-in verified customer, before linking. Profile address edits never rewrite order snapshots.

Account wishlist merges guest identifiers transactionally without replacing existing choices or deleting guest storage before persistence. Server account items never enter guest local storage; errors retain the guest list. Account/customer ID scopes every query; cross-account addresses/orders/returns are denied. Guest checkout and existing guest tracking remain independent and primary.

## Returns, inspection and stock
Both linked verified customers and verified guest tracking sessions may request an item-level partial return. Eligibility uses actual delivered fulfilment quantities/timestamps within the test window. Stable per-unit claims prevent duplicate/over-quantity requests and rounding drift. Allocate order discount proportionally across immutable item lines using cumulative integer allocation; each ordered unit has a deterministic net merchandise credit. Test refunds exclude outbound delivery/tax; approved merchant rules remain pending. Reason and resolution are explicit. Exchange variants must be active/published in the same product; recheck after inspection.

fulfilment.manage controls confirmed inspection: full requested physical quantity received, accepted resellable/damaged or rejected outcome, reason and active location. Only accepted resellable inspection restores original stock, once, in an append-only after-sales ledger; payment/refund callbacks never restock. Rejected claims release eligibility and refund nothing. Inspection and state changes are audited.

## Exchanges and money
After accepted inspection, staff reviews current target price/stock and signed price difference against the return credit. Reuse server Pricing plus Checkout reservation/settlement primitives. Equal/cheaper replacement orders use explicit exchange_credit funding linked to the original accepted return, never a fictional card payment. More expensive replacements remain awaiting_exchange_payment and cannot dispatch while Stripe top-ups are deferred; thirty-minute unpaid holds expire safely. Missing target stock yields recoverable failure without oversell. A failed/unissued exchange can explicitly switch to refund with reason. Replacement allocation reduces the original return refundable amount, so credit cannot be spent twice. Cheaper replacements leave the difference eligible for a controlled partial refund. Exchange-credited orders can dispatch only with a valid funding link.

## Refund sandbox
finance.refund controls review and explicit amount/reason confirmation. Lock order and return balances; pending/unknown/succeeded attempts reserve the eligible credit and aggregate order cap. Operation UUID/fingerprint plus unique durable provider receipt make retries idempotent. Local sandbox scenarios succeed/pending/fail/timeout-after-once; verify stored provider evidence amount/currency/order/identity before sandbox_succeeded. Keep sandbox states visibly distinct from real refunded money. Failed results release allocation; pending/unknown do not. Reconciliation polls sandbox receipts and never trusts a browser success flag. Real refund adapter/live money remain disabled pending Stripe integration and merchant policy approval.

## Verification refinement: permanent delivered-unit identity

A cancellation regression identified that filtering cancelled earlier parcels can shift a later parcel's ordinal position. Claims now bind a unique immutable fulfilment_item_id + delivery_unit pair as physical evidence, separately from the bounded original item credit slot. The requested event retains both proof and credit slots immutably. Cancelling an earlier unshipped parcel cannot make a previously claimed delivered unit eligible again; rejected inspection releases the claim but keeps its event history. Additive migration 000005 introduces this mapping before any development claims exist and fails safely if legacy claims would require a guessed mapping. The development database was backed up again and verified empty before applying it. Original order snapshots remain unchanged.


Account saved-list hydration preserves the public catalogue limit of 50 identifiers per request by batching the larger account list. A rejected/overflowed merge retains guest storage and still loads existing account choices, allowing removal followed by retry. Production browser checks cover a 56-item list and a full 500-item account plus an overflowing guest choice, including successful retry after freeing one slot. Account identity refresh generations also ignore delayed prior-account API responses after logout/login.
